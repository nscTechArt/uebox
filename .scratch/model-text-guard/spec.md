# Spec：给模型读的工具说明加术语守卫

Status: ready-for-agent

术语见根目录 `CONTEXT.md`。实现以 Implementation Decisions 与 Testing Decisions 为准；User Stories 只说明为什么做。
需要追溯某个词为什么被禁、或 #44 第 7 组怎么清理工具文字时，才读 `.scratch/chat-terminology/spec.md`。
文中事实（工具清单、现有命中）均已在 `upstream/main` 上核对（2026-10-15）。

## Problem Statement

用户在 AI 助手里看到的话，有一部分不是界面文案，而是模型转述的：模型读工具说明，会把里面的说法原样转告用户。
PR #44 把界面文案统一成「对话」，也一次性清理过工具说明里指对话的「会话 / 聊天」，但工具说明没有守卫。
界面文案有术语守卫兜着，写错就测试变红；工具说明没有，上游写新工具、改旧说明时把旧词带回来，没有任何检查会报。
#44 实测：首发后两周上游新写进约 8 行旧词（约每周 4 行），之后又出现一处。结果是用户在界面上看到「对话」，
AI 回话里又说「会话」，又回到「这是不是另一种东西」的困惑。

贡献者写工具说明时没人告诉他哪些词不能用；维护者只能在评审时靠肉眼发现，或者隔一段时间再做一次清理。

## Solution

给模型读的工具说明加一道零容忍的术语守卫，与界面文案的术语守卫用同一张禁用词表、同一套匹配规则：
扫描模型能拿到的全部自家工具的说明与参数说明，一出现禁用词就变红，逐条报出哪个工具、哪个位置、命中了什么、该换成什么。
其他领域的正当用法优先改写成不含禁用词的说法；改写不了的进一个很短、每条写明理由的白名单。

## User Stories

1. 作为中文用户，我希望 AI 转告我的话里指对话时说「对话」，这样它和界面上的叫法一致，我不必猜「会话」是不是另一种东西。
2. 作为英文用户，我希望 AI 转告我的话里指对话时说 chat，而不是 session 或 conversation。
3. 作为用户，我希望 AI 提到编辑器、试玩这些引擎里的东西时用准确的说法，而不是借用「会话」，这样我分得清它说的是对话还是引擎。
4. 作为用户，我希望 AI 向我提问（反问卡片）时用的说法与界面一致，因为这是它直接对我说的话。
5. 作为用户，我希望语音派活时 AI 口头汇报进度用的说法与界面一致，因为那是念给我听的。
6. 作为用户，我希望 AI 在把对话换到另一个工程时，说的「对话」和侧边栏里的「对话」是同一个东西。
7. 作为用户，我希望 AI 更新任务清单、收尾提问时用的说法与界面一致。
8. 作为用户，我希望工作室模式里 AI 转述队员、任务板的情况时用同一套词。
9. 作为用户，我希望 AI 用浏览器、知识库、子任务时的说法也一致，不因工具来自哪里而不同。
10. 作为用户，我希望术语一致在以后的版本里也保持住，而不是清理一次、过几周又漂回去。
11. 作为贡献者，我希望写新工具或改工具说明时，测试直接告诉我哪个词不能用、该换成什么，这样我不用先读完词汇表。
12. 作为贡献者，我希望报错指出是哪个工具、说明里还是哪个参数的说明，这样我能直接定位到要改的那句。
13. 作为贡献者，我希望参数名、枚举值这些协议值不被当成文案扫描，这样我不会被迫去改一个改了就会出错的协议名。
14. 作为贡献者，我希望守卫的规则与界面文案守卫完全一样，这样我只需要学一套规则。
15. 作为贡献者，我希望碰上改写不了的正当用法时，有明确的做法：进白名单并写理由，由评审把关。
16. 作为贡献者，我希望在注册表外新建工具并登记工具名后，守卫自动提醒我把它纳入扫描，而不是靠我记得。
17. 作为维护者，我希望两个守卫共用一张禁用词表，这样改词表只改一处，不会出现两张表慢慢对不上。
18. 作为维护者，我希望词汇表 `CONTEXT.md` 里指向守卫的说明仍然准确，改 _Avoid_ 时知道要同步哪一处。
19. 作为维护者，我希望守卫零容忍、不带基线文件，这样不会多出一个需要多会话协调的共享基线。
20. 作为维护者，我希望白名单不悬空：对应文字改写后，失效的白名单条目会被报出来。
21. 作为维护者，我希望守卫扫得到它声称要扫的每一个工具，某个工具改名或某个来源变空时测试能立刻发现，而不是安静地少扫。
22. 作为维护者，我希望这次改动只是一个小 PR，只做守卫和让守卫变绿所需的改写。
23. 作为 owner，我希望 PR 描述讲清楚守卫覆盖哪些工具、不覆盖哪些文字，这样我能决定后续要不要扩大范围。
24. 作为读代码的 agent，我希望工具说明里的术语与 `CONTEXT.md` 一致，这样我读工具说明时不会把「会话」误读成另一层概念。
25. 作为模型（工具说明的读者），我希望工具说明里对同一个概念始终用同一个词，这样我转述给用户时不会混用。

## Implementation Decisions

### 共用的禁用词模块

- 现有界面文案守卫里的禁用词表、单条禁用词的类型、叶子文字的类型、匹配函数、扫描函数，原样搬到 shared 层的一个新模块。
  逻辑、词表内容、失败信息格式一字不改；词表上方的注释一并搬过去。
- 放在 shared 层：它同时在主进程与渲染层两个类型检查项目里，是两个守卫测试都能通过类型检查的唯一位置。
  模块头写明它只给两个术语守卫测试用。
- 对外暴露禁用词表、禁用词类型、叶子类型、扫描函数；匹配细节留在模块内部。
- 界面文案守卫改为从共用模块导入；叶子收集、文案来源、它自己的白名单与全部用例留在原处，断言不变。
- `CONTEXT.md` 里「改 _Avoid_ 时同步守卫禁用词表」那句，指向改为共用模块，并说明它同时被两个守卫使用。

### 工具说明守卫：扫描对象

模型能拿到的全部自家工具，分三类来源：

- **工具注册表**：带上「渲染层发送方」与「知识库范围」两种依赖去造，依赖发送方的笔记工具、绑了知识库才注册的知识库工具
  才会出现。知识库存入工具的说明随范围变化，「全库范围」与「单个知识库」各造一遍；两次都出现的工具按「位置 + 文字」去重。
- **已登记工具名的注册表外工具**：注册表模块里的「全部工具名」函数（给技能体检用、不看运行时条件的那份清单）已经登记了
  在 agent 装配时现造的工具：技能加载与技能资源读取、子任务、工具搜索、浏览器工具、反问用户、切换对话归属的工程、
  更新任务清单（`update_plan`）、收尾提问（`wrap_up`）。逐个直接调用它们的工厂。技能工具在技能清单为空时不造，给一条假技能。
- **未登记工具名的注册表外工具**：口头汇报进度（`voice_report`）、工作室模式的制作人工具与队员工具。这几个靠显式列出，
  测试文件头写明它们是人工维护的。

工厂直接调用，桩依赖只需满足类型：说明文字是写死的常量或字面量（制作人招人工具会把传入的命名空间写进说明，桩给一个即可），
依赖只在执行时使用。agent 装配本身太重（模型选择、技能发现、MCP），守卫在它下面一层取工具。

### 工具说明守卫：扫描内容与匹配

- 工具说明，位置记为「工具名.description」。
- 参数说明：递归遍历参数 schema，收集键名为 description 且值为字符串的项，位置记为「工具名.parameters.」加从根到该项的键路径。
  名为 description 的参数（值是 schema 对象）本身不是文字，它内部的说明字符串照样收集。参数名、枚举值、默认值、示例是
  给模型的协议值，不在收集范围内。
- 复用共用模块的扫描函数，零容忍，失败信息逐条给出位置、命中词、替换建议。

### 白名单

按完整位置精确匹配、按禁用词条目放行，语义与界面文案守卫的白名单相同；每条旁边写理由。放行三处，全是英文 session：

- 性能采集工具说明里的 "Session Frontend"：UE 自带工具的名字。
- 打开工程工具说明里的 `session-scoped`：回执里「切换被挡住」原因码的原文，模型要拿回执里的同一串去对照。
- 切换对话归属工程的工具说明里的 `session-scoped`：同上。

具体位置以守卫实际报出的为准。

### 改写现有命中

工具说明里的中文命中只有三句其他领域的正当用法，只换词、句子其余部分不动：

- C++ 编译能力探测工具的说明：「这个编辑器会话该走哪条编译路」→「这个编辑器进程该走哪条编译路」。
- 自动试玩工具的说明：「不接管别人的会话」→「不接管别人开的试玩」。
- 试玩工具的说明：「这个工具不接管别人的会话」→「这个工具不接管别人开的试玩」。
  原文指用户自己在编辑器里按了 Play / Simulate 的那次运行。

断言这几句原文的已有测试随文字一起改。

### 完成与升级

**完成**，以下全部成立：

- 新守卫的四条用例（见 Testing Decisions）全绿；界面文案守卫、工具名引用测试原样全绿。
- 改写过说明的工具所在模块的已有测试全绿。
- 主进程与渲染层两侧类型检查通过。
- 反向验证做过：在某个工具说明里临时写入「新会话」，守卫变红且信息含工具名与「对话」建议；撤回后恢复绿色。

**停下来报告**，碰上任一种就停，附完整信息，等 lead 决定：

- 守卫报出上面三句改写与三处白名单之外的命中（附完整清单）。
- 任一工厂在测试里造不出来，或测试进程崩溃（附报错与引起它的导入）。

## Testing Decisions

- **好测试的标准**：只断言外部可见的结果，也就是模型实际读到的工具说明和参数说明里有没有禁用词。整句措辞是文案选择，
  在 diff 里审。
- **测试接缝：模型拿到的工具对象**，只有这一个。共用禁用词模块是把现有测试里的数据和函数挪到一处，不是新接缝。
- **新守卫的用例**：
  1. 扫得到工具：总数大于 50；「全部工具名」函数返回的每个名字都在收集结果里；三个显式列出的来源各至少贡献一个工具。
  2. 提取规则自证（内联小样例）：嵌套参数说明被收集且位置正确；名为 session 的参数键不被收集；枚举值 session 不被收集；
     名为 description 的参数内部的说明字符串被收集。
  3. 零命中：全部收集到的文字过扫描函数，失败清单为空。
  4. 白名单不悬空：白名单里每个位置都在收集结果里，且该位置的文字确实命中它放行的条目。
- 匹配规则本身（汉字子串、英文整词不分大小写、插值占位符剥离、白名单语义）由界面文案守卫的自证用例覆盖。
- **先例**：
  - 「工具描述里不许出现不存在的工具名」测试：照它从注册表取工具对象的方式。
  - 界面文案的术语守卫：同一套规则、白名单语义与失败信息格式。

## Out of Scope

- 工具回执与工具报错（动态拼接的文字，要按 AST 提取，留给上游决定是否另做）。
- 系统提示，包括工具搜索规则里现有的一处 "across this conversation"。
- 语音前台指令、渲染层交给实时语音模型的文字；「当前语音对话」标记一对必须成对保留（见 #44）。
- 应用内技能文本、CLI 的技能文本。
- 第三方 MCP 工具的说明（文字不是我们写的）。
- 注释与日志；主进程其余部分、CLI、`docs/`：按 `CONTEXT.md` 的约定，那里的「会话」多指内核 session 或 MCP 会话，本来就算对。
- 修改禁用词表的内容、界面文案守卫的匹配规则或它的白名单。
- 守卫的通用例外机制（如按领域放行 session）。

## Further Notes

- 范围来自 owner 的答复：只给模型读的工具说明加守卫，正当用法优先改写，改不了的进短白名单并写理由。
  「注册表外现造的工具也算在内」是本 spec 的判断：owner 的目标是「模型读到的工具说明」，且反问、口头汇报、切换工程归属
  离用户最近；owner 不同意时删几行即可收回。
- PR 描述写明：覆盖的工具来源（三类，逐个列出注册表外工具）、Out of Scope 各项、白名单每条及理由，
  并附系统提示里 "across this conversation" 的现有命中，由 owner 决定是否顺手改。
