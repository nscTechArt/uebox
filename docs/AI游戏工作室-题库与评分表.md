## 1. 题库

每道题只给一句话，不给参考图，不说明玩法，也不划范围。模型要自己补全这些空白，这本身就是考察内容。一半题目点名"类似某作"，考它能不能从一个作品名里提炼出玩法；另一半只报题材，考它能不能自己拿主意。

| id | 题材 | 形式 | 题面 |
|---|---|---|---|
| `platformer-3d` | 3D 平台跳跃 | 类比 | 做一个类似《超级马里奥奥德赛》的 3D 平台跳跃游戏 |
| `roguelike-topdown` | 俯视角 Roguelike | 题材 | 做一个俯视角的 Roguelike 射击游戏 |
| `tower-defense` | 塔防 | 题材 | 做一个塔防游戏 |
| `kart-racing` | 赛车 | 类比 | 做一个类似《跑跑卡丁车》的赛车游戏 |
| `puzzle-fp` | 第一人称解谜 | 类比 | 做一个类似《传送门》的第一人称解谜游戏 |
| `horror-explore` | 恐怖探索 | 题材 | 做一个恐怖探索游戏 |
| `management-sim` | 模拟经营 | 题材 | 做一个模拟经营游戏 |
| `survivor-like` | 割草生存 | 类比 | 做一个类似《吸血鬼幸存者》的 3D 割草游戏 |

- 题面以 `cases.mjs` 为准，本表只是抄录。**开跑之后不许改题面**，要换题就加一个新的 id。
- 每道题还带一条评分参考（`hint`），写的是这类游戏常见的核心循环。它只给评分的人看，不进题面。模型自己立的玩法和参考不一样没关系，按它自己立的那套评。

## 2. 跑法

1. 用 `pnpm dev:ue-verify` 启动盒子。这样会开启本机调试 HTTP，采集时要用它调引擎。
2. 关掉所有 UE 编辑器，让模型自己新建工程。它要是在已有工程里干，这条样本作废。
3. 运行 `node tests/manual/game-studio/bench.mjs new <题目id> [--arm team|goal] [--model 名]`，建好这次的记录。
4. 在盒子里新开一个会话，把脚本打印出来的那一行原样贴进去（`/team 题面` 或 `/goal 题面`），之后不要插话。
5. 跑完后，保持这次工程的编辑器开着，运行 `bench.mjs collect <运行目录>`。脚本会采集过程指标和自动核验结果，写进 `score.md`。
6. **亲自玩一遍**，填 `score.md` 里的人工评分和观察。
7. 运行 `bench.mjs report`，汇总所有运行。

## 3. 评分表

### 3.1 人工评分：六项，每项 0 / 1 / 2 分

按模型**自己立项的玩法**来评，不按我们心里预设的样子评。

| 项 | 0 | 1 | 2 |
|---|---|---|---|
| 完整游戏循环 | 进不了游戏，或者玩起来没有目标 | 能玩，但缺胜负结局，或者结束后不能重来 | 开始 → 游玩 → 胜利或失败 → 重来，整条走得通 |
| 核心机制 | 核心玩法不成立 | 有，但缺胳膊少腿，或手感明显坏 | 这个题材该有的核心机制都能用 |
| 基础场景 | 空场景，或者一堆没摆好的方块 | 有可玩区域，但粗糙，或有空洞、能掉出世界 | 至少一个完整可玩的区域，没有明显穿帮 |
| 基础美术 | 全是默认材质，看不出风格 | 有美术，但风格不统一 | 风格统一，一眼能看出是什么游戏 |
| 基础数值 | 玩不下去：太难、太简单，或经济崩盘 | 能玩，但明显失衡 | 难度和成长大体合理 |
| 无明显 bug | 有严重 bug | 没有严重 bug，但一般 bug 超过 2 个 | 没有严重 bug，一般 bug 不超过 2 个 |

- **严重 bug**：崩溃、卡死、软锁（进入无法继续的状态）、没法继续玩。
- **一般 bug**：不影响继续游玩的表现问题，比如穿模、错位、提示不对。
- bug 这一项不直接打分，只填两个计数，分数由脚本算出来。

**达标 = 没有 0 分项，且总分 ≥ 9/12**。9/12 约等于 75%，对应"做到七八成"。
短板项不能靠其他项补：一项 0 分，其他项分再高也不算达标。

### 3.2 另外记录，不计入达标

- **盲玩感受**：1～5 分，就是"好不好玩"的直觉。
- **验收结论**：`pass` / `fail` / `blocked` / `maxed`（到了轮数上限）/ `none`（没有验收这一步）。
  汇总时会单独数一个指标：**验收放行但没达标**，即验收员说过了，人玩下来却不达标。这是设计稿第 5 节那条"独立验收员"硬规则到底管不管用的直接证据。

### 3.3 自动核验：脚本来做，辅助人工

| 核验 | 怎么验 | 什么情况算不过 |
|---|---|---|
| 新建的工程 | `.uproject` 的创建时间是否晚于开跑时间 | 工程早于开跑，说明在已有工程里干的，**样本作废** |
| 崩溃 | 工程 `Saved/Crashes` 下开跑后新增的记录 | 有新增 |
| 蓝图全部编译通过 | `blueprint_compile_all`（全量） | 有编译错误 |
| 冒烟试玩 | `ue_playtest` 跑 30 秒，抓 9 帧拼成时间轴图 | 没跑满 30 秒，或出现运行时错误 |

拿不到结果的核验记"—"（没验到），**既不算通过，也不算失败**。

自动核验和人工评分对不上时，比如人工给了 bug 满分、冒烟却报了运行时错误，以人工为准，但要在观察里写清楚为什么。

### 3.4 过程指标：从会话记录里算

- **用时**：第一条消息到最后一条消息之间的时长。
- **消息数**：真人消息数和复核打回次数分开记。
- **工具调用**：总次数、失败次数、Python / 命令行兜底次数（占比高说明对口的工具不够用）、派子任务次数。
- **token 和费用**：只算主会话，子 Agent 不落会话记录。厂商没报价时费用记"—"，表示不知道，不代表免费。

### 3.5 观察：每次都写，这是题库最主要的产出

- 它怎么拆的：立项、玩法、范围、先后顺序。
- 卡在哪，绕了哪些路。
- 缺什么：工具、素材、能力。
- 它说做完了，实际差在哪。

这些观察会直接变成两份清单：设计稿附录里的规则台账，以及下一步要补的能力。
