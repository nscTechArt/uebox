# AI 游戏工作室设计（2026-09-25）

**状态**：P0 题库完成；`/team` 第一版已实现（见第 9 节），还没真机跑过题库。代码位置按 2026-09-25 的 `main` 核对。

---

## 0. 结论先行

用户只给一句话，比如"做一个类似马里奥奥德赛的游戏"，没有参考图，也没有玩法说明。盒子自己组一支 Agent 团队，从立项一路做到交付一个**可玩的阶段 MVP**。

**核心原则：盒子不管脑子，只管手脚和环境。**

- **交给模型**：岗位怎么分、流程怎么走、题材怎么打、先做什么后做什么、范围怎么砍。这些都由模型决定，盒子不预设。
- **盒子负责**：模型自己变不出来的东西。能拉起队友，能动手（操作 UE）、能看见结果，遵守编辑器只有一台这类物理规则，能连续跑几小时不失忆，花费和进度对用户可见。

原因：通用游戏开发没有固定形态。写死的岗位、流程和打法，只能覆盖我们想得到的题材，还会替模型做它本来做得更好的决定。模型能力在涨，约束应该越来越少，而不是越来越多。

## 1. 目标：交付标准

完成度只要求 70～80%，剩下的留给用户打磨。交付物必须满足下面五条：

| 项 | 含义 |
|---|---|
| 完整游戏循环 | 开始 → 游玩 → 胜利或失败 → 能重来 |
| 核心机制 | 立项时定下的机制都能用 |
| 基础场景与美术 | 至少一个完整可玩的区域，风格统一 |
| 基础数值 | 难度和成长大体合理，不会崩盘或卡关 |
| 无明显 bug | 不崩溃、不卡死、不软锁，编译零错误 |

交付时附带三样东西：
- 打包好的游戏
- 交付报告：做了什么、没做成什么、花了多少
- **给用户的打磨清单**：剩下 20% 从哪里下手，哪些参数可以调

---

## 2. 非目标

- **不预设岗位、流程、里程碑，也不预设题材打法。** 这些全部交给模型。
- **不追求商业品质。**
- **不在用户已有的项目里干活**，只在新建的工程里干。
- **暂不做多个编辑器实例并行。** UE 资产是二进制文件，两份工程各改各的，最后合不回来。

---

## 3. 用户看到什么

1. 在助手的输入框里打 `/team 一句话`，开启工作室模式。这个入口和 `/goal` 并列，互不影响，`/goal` 保持原样。
2. 制作人（主 Agent）自己立项、拉队员、分活。立项书、任务板、每个队员在做什么，全程都能看到。
3. 默认全自动。用户可以随时插话，比如"主角换成猫"，由制作人判断影响哪些活并重新安排；也可以暂停、接管，或者直接和某个队员对话。
4. 顶部始终显示花费和预算。
5. 结束时拿到第 1 节列出的交付物，外加一段试玩视频。

界面按"融进现有界面"的原则做：它是现有会话的一种，队员复用子任务泳道的展示方式，不另开新页面。

## 4. 盒子提供的五样东西

### 4.1 组队原语

制作人需要能随时拉起队员，并且：

- **给队员写人设**：人设由制作人现场写，盒子不给模板。
- **给队员选模型档位**：强、标准、快三档，映射到用户已绑定的模型；也可以直接钉死某个模型。
- **给队员划工具范围**：按命名空间或工具名划；可以设为只读；并决定这个队员能不能碰编辑器。
- **队员常驻**：每个队员有自己的会话记录，可以连续干多件活，也可以被解散。现在的子任务是一次性的，做完就没了。
- **队员之间互发消息**，制作人能向任一队员插话。
- **共享任务板**：记录每件活的负责人、依赖关系、状态和证据。任务板放在工程目录里，界面直接读它。
- **共享工作区**：工程里的 `.uebox/studio/` 目录所有队员都能看到。里面放什么由模型决定，比如立项书、美术圣经、参考图、决策日志。

嵌套一层：只有制作人能组队；队员可以用现有的 `task` 工具派一次性子任务，但不能再组队。

### 4.2 手和眼

大部分已经有了：新建工程（带引擎模板）、C++ 编译、蓝图、关卡、Actor、UI、输入、进 PIE 试玩（`ue_autoplay`）、截图、生图、生 3D、生视频、资产库、上网、本地命令行、任务转视频。

还缺：

- **打包出可执行文件**。目前只能走命令行调 UAT，没有专门的工具。
- **读取 PIE 的运行日志和报错**，给验收用。现有能力是否够用待核实。

### 4.3 物理规则

这些不是方法论，是现实限制，模型绕不开，所以由盒子兜底。

- **编辑器钥匙**：同一个编辑器同一时间只允许一个队员写。其他队员排队等，拿不到钥匙时等待，而不是立刻报失败。PIE 试玩期间，钥匙归试玩者独占。
- **资产归属锁按队员算**。现在同一个会话里的所有子 Agent 共用一把锁，互相不设防。
- **快照与回滚**：每完成一件活自动存一次快照，改坏了能退回去。
- **崩溃恢复**：编辑器断线后自动重开工程，把出错信息交还给出错的那个队员。
- **写入范围**：只允许写本次新建的工程和盒子的工作区。

### 4.4 长跑底座

- **断点续跑**：任务板、工作区和各队员的会话记录都落盘。盒子重启或电脑重启后，能从中断处接着干。
- **上下文满了能接着干**。现有的压缩机制要确认在跑几小时的场景下是否够用。Anthropic 的实验里，压缩不够时改用"清空上下文、带着存档状态重来"。
- **卡住检测**：某个队员连续多轮没有进展，就通知制作人。怎么处理由制作人决定，盒子不替它决定。

### 4.5 预算与可见性

- 总预算封顶，token 和生成类花费分开计。花到 80% 时提醒制作人；到 100% 暂停，等用户决定。
- 按队员显示花费。
- 审批：制作会话内，对工程目录的写操作默认放行，靠写入范围兜底。生成类花费改为走总预算，不再逐次确认。

## 5. 唯一一条硬规则：交付要有证据

制作人宣布交付时，盒子启动一个**独立验收员**。它有三个特点：
- 没有参与制作，不带制作过程的上下文
- 只拿到第 1 节的交付标准和打包好的游戏
- 自己去玩，录像，给出通过或不通过

不通过时，把验收意见交还给制作人，由它继续修。

为什么要有这条：模型给自己的作品打分天然偏宽。这不是能力问题，更强的模型也一样。这条规则只规定"说做完了要拿得出证据"，不规定怎么做。实现上可以直接复用 `/goal` 验收员的模式：全新上下文、固定工具白名单、给出判定、结果回灌。

---

## 6. 规则怎么加、怎么删

- **先放开跑。** 翻车了再加规则，每条规则都要对应一次真实的翻车。
- **记台账。** 放在本文附录，每条记五项：翻车现象、加了什么规则、在哪个模型下加的、加完之后的效果、什么时候复查。
- **换 SOTA 模型后逐条拆掉重测**，不再起作用的就删掉。

## 10. 开放问题

1. **快照怎么做？** 在工程里用 git 自动提交最简单，但二进制资产会让仓库变大。另一个选择是盒子自己按改动的文件做备份。
2. **编辑器崩溃后自动重开，现有能力够不够？** 能打开工程，但"检测到崩溃 → 重开 → 等插件重连"这条链路没有验证过。
3. **会动的角色从哪来？** 怎么做由模型决定，但环境得有料可用：引擎模板里的角色，资产库里可以重定向的角色和动画，够不够用？
4. **队员人设写在哪？** 选项一：直接作为系统提示词里的一段；选项二：用现有技能文件的格式存下来，下个项目还能复用。
5. **默认预算设多少？** 参考数字：Anthropic 的三 Agent 实验，一个复古游戏编辑器跑 6 小时，花了 200 美元。
