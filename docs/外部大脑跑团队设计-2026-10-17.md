# 外部大脑跑团队设计（2026-10-17）

> 本稿和代码从 GDBox 同名设计移植到虚幻盒子（2026-10-17）。和 GDBox 版的出入：制作人可以用 `project_manage`
> 建工程、开工程（和盒子里 `producerTools()` 同一个口径）；验收结论只记在 `external.json`，不进团队事件账

## 0. 结论先行

**一句话：Claude Code 当大脑，盒子当工作室。**

- 想要的效果：用户在 Claude Code 里开一个团队，制作人、队员、验收员的每一次思考都花用户自己 Claude 订阅的额度，盒子一个 token 都不花。
- 做法：盒子不再替团队调模型，只提供团队的「场地」—— 名册、任务板、留言、文件锁、编辑器钥匙、快照、交付闸。思考全在 Claude Code 里：主会话当制作人，子 Agent 当队员和验收员。
- 盒子里的界面照常能看任务板和进度，用户随时能看、能停、能退回快照。
- 不改盒子内置的 `/team`。两种团队共用同一套落盘格式和面板，区别只在「谁在思考」。

## 1. 为什么是这条路

要让 Claude 的额度跑团队，只有三条路，前两条走不通：

| 路线 | 结论 | 原因 |
|---|---|---|
| 盒子照常跑团队，模型请求通过 MCP sampling 交给 Claude Code | 不行 | Claude Code 不支持 MCP sampling（[claude-code#1785](https://github.com/anthropics/claude-code/issues/1785) 未关）。规范本身也要求每次 sampling 有人可以拒绝，几小时的团队跑不下去 |
| 盒子用 Claude 订阅登录，或者拉起 `claude -p` / Agent SDK 当模型来源 | 不行 | Anthropic 明文不允许第三方应用提供 Claude.ai 登录、或替用户把请求走 Pro/Max 订阅（[Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance.md)）。盒子是公开发布的应用，`oauth.ts` 里也有意没有 Anthropic 这一家 |
| **用户自己开官方 Claude Code，连盒子的 MCP，由 Claude Code 编排团队** | **可行** | 用户用官方客户端登录自己的订阅，这是允许的用法；盒子只是 Claude Code 调用的工具 |

第三条也不限于 Claude Code。任何能拉起子 Agent、能连 MCP 的客户端（Codex 等）都能用同一套工具，本稿以 Claude Code 为准，其它客户端放在第 9 节。

## 2. 现状：团队里哪些东西调模型

团队工具一共七个（`TEAM_TOOL_NAMES`，[teamTools.ts](../src/main/agent-v3/core/team/teamTools.ts)）：

| 工具 | 调不调模型 | 说明 |
|---|---|---|
| `team_hire` | 不调（但要挑模型） | 名册上加一个人，同时给它配一个盒子里的模型 |
| `team_send` | **调** | 用队员的模型跑一个子 Agent（`runMember`），干完自动存快照（`autoSnapshot`） |
| `team_deliver` | **调** | 用另一个模型跑验收员（`runAcceptance`，[createAgent.ts](../src/main/agent-v3/core/createAgent.ts) 里接线） |
| `team_board` | 不调 | 读写任务板 |
| `team_message` | 不调 | 队员之间、队员和制作人之间留言 |
| `team_snapshot` | 不调 | 列出 / 手动存 / 退回工程快照 |
| `team_status` | 不调 | 团队近况 |

另外三样场地设施也不调模型，外部团队可以原样用：

- **文件锁**（`assetLock.ts`）：锁的主人是 `<团队根会话>` + `MATE` + `<队员名>`，同一个文件两个队员同时改，后来的立刻失败。
- **编辑器钥匙**（`editorKey.ts`）：同一个编辑器一次只放一个写操作进去，拿不到就排队。
- **交付闸**（`teamSession.ts`）：没过验收不算交付，制作人收尾时还没过就推回去，一轮最多推两次（`MAX_TEAM_NUDGES`）。

外部团队要做的就是：**留下不调模型的部分，把 `team_send` 和 `team_deliver` 里「调模型」的那一半交还给客户端。**

## 3. 角色映射

| 盒子内置团队 | 外部团队（Claude Code） |
|---|---|
| 制作人：盒子里那条对话 | Claude Code 的主会话 |
| 队员：`team_send` 拉起的子 Agent，盒子的模型 | Claude Code 的子 Agent（`member` 定义），Claude 模型 |
| 验收员：`team_deliver` 里拉起的独立 Agent | Claude Code 的子 Agent（`acceptor` 定义），只读 |
| 队员记忆：盒子存的整段对话，下次派活喂回去 | 同一次 Claude Code 会话内续用同一个子 Agent；跨会话靠工作区文件、任务板、留言交接（见第 8 节） |
| 交付闸：盒子在收尾时推回 | Claude Code 的 Stop hook 问盒子要不要放行 |
| 制作人没有写工具 | 盒子拒绝制作人那条连接上的写工具 |

## 4. 关键设计：每个角色一条 MCP 连接

### 4.1 问题

Claude Code 的子 Agent 默认继承主会话的 MCP 工具，共用主会话的连接。盒子按连接（MCP 会话）认人，共用连接的话，盒子分不出这次写操作是哪个队员发的：文件锁全记在同一个人名下，两个队员改同一个文件挡不住；快照和活的账也记不到人头上。

给全部一百多个工具都加一个 `as` 参数改动太大，模型也会忘了填。

### 4.2 做法

**每个子 Agent 自己开一条连接，进门先报名字。**

Claude Code 的子 Agent 定义可以内联声明自己的 MCP server：内联的 server 随子 Agent 启动、随它结束，是独立的一条连接（[Subagents](https://code.claude.com/docs/en/sub-agents.md)）。于是：

1. 插件里的 `member` 子 Agent 定义内联一个 `uebox-member` server（和主会话连的是同一个盒子，只是另开一条连接），并且 `tools` 只放 `mcp__uebox-member__*` 加 Claude Code 自带的读文件类工具 —— 不继承主会话的 `uebox`，免得绕过身份。
2. 子 Agent 的第一步是调 `team_join`，报团队 id 和自己的名字。盒子把这条 MCP 会话绑定到这个队员：之后这条连接上的每次工具调用都套上 `runWithLockOwner(<团队 id> + MATE + <队员名>)` 和 `runWithEditorKey`，和内置团队里 `runMember` 的执行流一样。
3. 没调 `team_join` 的成员连接，除了 `team_join` 之外的工具一律拒绝，错误里写明下一步。
4. 主会话那条连接调 `team_open` 之后绑定为**制作人**。盒子按 `producerTools()` 的口径拒绝它的写工具：只读工具、绑工程、团队工具可以用，其余的要招人派出去。规则台账里记过两次「制作人拿着写工具自己把游戏写完」，这里由盒子把关，不靠提示词。

**真机待验证**：内联 server 是否确实另开连接、能否带鉴权头（见第 10 节第 1 条）。验证不过时的退路见第 10 节。

## 5. 工具

### 5.1 主会话（制作人）

| 工具 | 新 / 复用 | 作用 |
|---|---|---|
| `team_open` | 新 | 参数：`objective`、可选 `project_path`、可选 `team_id`。没给 `team_id` 就新建一个外部团队，给了就接着跑。把这条连接绑成制作人。返回团队 id、共享工作区路径、制作人简报（`buildProducerBrief` 改写，见 5.4）、交付标准（`DELIVERY_STANDARD`） |
| `team_hire` | 改 | 只登记：名字、人设、岗位类型、工具命名空间、是否只读。**不挑模型**，名册上的模型记成「外部」 |
| `team_board` / `team_message` / `team_snapshot` / `team_status` | 复用 | 原样。`team_message` 以制作人身份发 |

外部团队**没有** `team_send` 和 `team_deliver`：派活是制作人用 Claude Code 的 Agent 工具拉起 `member` 子 Agent，验收是拉起 `acceptor` 子 Agent。

### 5.2 队员连接

| 工具 | 新 / 复用 | 作用 |
|---|---|---|
| `team_join` | 新 | 参数：`team_id`、`member`、`brief`（这件活的说明）。名字必须在名册上（`PRODUCER`、`ACCEPTOR` 不许用）。开一件活（`startJob`），返回队员框架提示（`buildMemberFraming`）、收件箱里没读的留言（`takeInbox`）、任务板 |
| 盒子的全部业务工具 | 复用 | 按名册上这个人的命名空间白名单和只读设置收窄，跑在这个队员的锁主和编辑器钥匙下 |
| `team_board` / `team_message` / `team_status` | 复用 | 和内置团队里队员手上的三件一样 |
| `team_report` | 新 | 参数：`report`。交回这件活：`finishJob`，这件活里有写操作就自动存一份快照（复用 `autoSnapshot` 的逻辑），返回快照 id。之后这条连接解除绑定 |

队员不调 `team_report` 就结束的（被停下、子 Agent 报错），连接断开时盒子按「停下」收这件活（`finishJob` 的 `stopped`），和内置团队里活被打断的口径一样。

### 5.3 验收员连接

| 工具 | 新 / 复用 | 作用 |
|---|---|---|
| `team_join` | 同上 | `member` 填 `acceptor`。这条连接绑成**只读**（等同 Ask 模式）。返回验收提示（`buildAcceptancePrompt`），参数里的交付说明、怎么玩、工程路径由制作人在派验收员时写进子 Agent 的任务 |
| 盒子的只读工具 | 复用 | 无头试玩、截图、读场景这些 |
| `team_verdict` | 新 | 参数：`verdict`（`PASS` / `FAIL` / `BLOCKED`）、`findings`。写进团队状态（复用 `applyVerdict`） |

`team_verdict` 的三道把关，由盒子做，不靠提示词：

1. 只有绑成 `acceptor` 的连接能调。制作人和队员连接调了直接拒绝。
2. 验收员连接是只读的，所以它不可能「边验边改」。
3. 验收时刻记成 `verdictAt`。之后任何队员再写工程（`lastWriteAt` 更新），这次 PASS 就作废，要重新验 —— 和内置团队里「验收之后改没改过」的判法一样。

### 5.4 提示词怎么搬

[teamPrompt.ts](../src/main/agent-v3/core/team/teamPrompt.ts) 里的四段（`DELIVERY_STANDARD`、`buildProducerBrief`、`buildMemberFraming`、`buildAcceptancePrompt`）**留在盒子里，由工具返回**，不抄进插件。这样：

- 两种团队读的是同一份规矩，盒子改了规矩，外部团队下一次 `team_open` / `team_join` 就拿到新的；
- 插件里的提示词只管 Claude Code 这一侧的事：怎么拉子 Agent、子 Agent 第一步先 `team_join`、干完 `team_report`。

制作人简报要改的地方：把「用 `team_send` 派活」「用 `team_deliver` 交付」换成「用 Agent 工具拉起 `member` / `acceptor`」。用一个参数区分两种团队，不复制一份。

## 6. 交付闸

内置团队的交付闸在盒子的 agent 循环里（`createTeamGate`）。外部团队的循环在 Claude Code 里，闸要挪到 Claude Code 的 **Stop hook**：

1. 插件注册一个 Stop hook，跑 `uebox team gate <团队 id> --json`。
2. CLI 问盒子要不要放行。盒子按 `TeamState` 判：
   - 没有验收结论，或者结论不是 PASS → 拦；
   - PASS 之后又写过工程 → 拦；
   - 这一轮已经拦过两次（`MAX_TEAM_NUDGES`）→ 放行，让制作人停下来跟用户说清楚卡在哪；
   - 结论是 BLOCKED → 放行（就是要停下来问用户）。
3. 拦的时候 hook 返回 `{"decision": "block", "reason": "<盒子给的那句话>"}`，Claude Code 会接着跑。
4. 「一轮」从哪算：Claude Code 的 UserPromptSubmit hook 跑 `uebox team round <团队 id>`，清零 `nudges`、记 `roundStartedAt` —— 和内置团队「每条真人消息清零」一样。

团队 id 怎么交给 hook：`team_open` 返回 id 后，插件的提示词要求制作人把它写进 `<工程>/.uebox/team-id`（或共享工作区）。hook 从当前目录往上找这个文件；没有就直接放行 —— 不是团队会话，不该拦。

`TeamState` 现在存在会话的执行记录里（`options.team`）。外部团队没有盒子侧的会话，改成存在 `<团队>.team/state.json`。

## 7. 盒子界面

- 外部团队的落盘位置用 `teamDirsFor(<团队 id>)`，团队 id 形如 `ext-<uuid>`，和内置团队一样分成状态目录和共享工作区。
- 任务板面板（`TeamBoardPanel.vue`）按会话 id 读 `agent-v3:team-state`。外部团队没有盒子里的对话，所以在助手页加一个「外部团队」入口，列出 `ext-*` 团队，点开用同一个面板。
- 面板上和内置团队不同的地方：
  - 模型一栏显示「外部（Claude Code）」，不提供换模型；
  - 用量一栏显示「外部模型，盒子不计」—— 盒子看不到 Claude 的 token；
  - 「重开」「退回快照」照常可用；「结束团队」只是把团队标成结束，停不了 Claude Code（提示用户去 Claude Code 里停）。
- 队员正在干什么（`teamLive`）：外部队员的工具调用都经过盒子，照样能推实时活动；拿不到的是模型的思考文字。

## 8. 记忆和断点续跑

内置团队里队员的记忆是盒子存下的整段对话（`saveHistory`），下次派活喂回去。外部团队盒子拿不到 Claude 的对话：

- **同一次 Claude Code 会话内**：制作人用 SendMessage 续用同一个子 Agent，记忆在 Claude Code 那边。
- **跨会话**（Claude Code 退出、换一天接着做）：靠盒子里留得住的东西 —— 共享工作区里的立项书、决策日志，任务板，留言，活的账（`jobs` 里的 `report`）。`team_join` 返回时附上这个队员最近几件活的交回报告，相当于交接纪要。
- 盒子重启：名册、任务板、状态都在盘上。正在进行的活按「停下」收；Claude Code 那边的子 Agent 下一次调工具会发现连接断了，要重新 `team_join`。

**不做**：把 Claude Code 的对话回传给盒子存。那要求客户端每轮上报全文，Claude Code 没有这样的接口，靠提示词让模型自己抄一遍也不可靠。

## 9. 插件和 CLI

### 9.1 Claude Code 插件

和 `packages/cli/skills` 放在一起发布，内容：

| 部分 | 内容 |
|---|---|
| 技能 `uebox-team` | 制作人的打法：先 `team_open`，招人用 `team_hire`，派活用 Agent 工具拉 `member`，交付前拉 `acceptor`，团队 id 写进 `.uebox/team-id`。规矩本身由 `team_open` 返回，这里不重复 |
| 子 Agent `member` | 内联 `uebox-member` server；第一步 `team_join`，最后一步 `team_report` |
| 子 Agent `acceptor` | 内联 `uebox-member` server；第一步 `team_join`（`acceptor`），最后一步 `team_verdict` |
| Stop hook | `uebox team gate`（第 6 节） |
| UserPromptSubmit hook | `uebox team round`（第 6 节） |

鉴权：内联 server 的令牌从环境变量读（例如 `UEBOX_TOKEN`），不写进插件文件。具体写法等第 10 节第 1 条验证后定。

### 9.2 CLI 新命令

| 命令 | 读 / 写 | 作用 |
|---|---|---|
| `uebox team list` | 读 | 列出外部团队 |
| `uebox team status <id>` | 读 | 任务板、验收结论、在干的活 |
| `uebox team gate <id>` | 只动团队状态 | 交付闸判定，拦的时候 `nudges` 加一 |
| `uebox team round <id>` | 只动团队状态 | 新一轮开始，清零 |

`gate` / `round` 只改团队自己的状态文件，不碰工程，不要求 `--allow-write`（hook 里每轮都跑，加开关只会让人图省事全开）。

### 9.3 其它客户端

工具是通用的，换客户端只换编排那一层。Codex 等客户端要看它能不能给子 Agent 单独开 MCP 连接；不能的话走第 10 节第 1 条的退路。本期只做 Claude Code。

## 10. 待定和风险

1. **内联 server 是否另开连接、能否带鉴权头**（关键）。文档写了内联 server 随子 Agent 起停，没写明连接是否独立。动手前先真机验证。
   退路：成员身份改成每次调用都带一个 `team_as` 参数，只加在写工具的调用路径上（MCP 层统一剥离，业务工具不感知）。代价是模型可能漏填，漏填时按「无主」拒绝写操作。
2. **制作人仍可以不派人、自己让主会话干活**：主会话连接上的写工具已被盒子拒绝，但 Claude Code 自带的 Write / Edit / Bash 能直接改工程文件，盒子管不到。缓解：插件技能里写明；`team_status` 里显示「有工程改动不属于任何队员」（快照对比时发现未登记的写入）。不能根治，记在这里。
3. **验收员的独立性**：盒子能保证验收员连接只读、没参与写入，保证不了 Claude Code 给验收员的任务里没有夹带「这个已经好了」的暗示。和内置团队里制作人写交付说明的风险相同，不额外处理。
4. **用量**：盒子看不到 Claude 的 token，任务板的用量栏对外部团队无意义。不去估算。
5. **`gen_*` 生成类工具仍然花钱**：它们调的是盒子里配好的生成服务，跟谁在思考无关。`team_open` 返回的简报里要写清楚。
6. **并发**：几个子 Agent 同时打盒子，受文件锁和编辑器钥匙约束，和内置团队一样。盒子的模型请求调度（`requestGate.ts`）不参与，外部团队不经过它。
7. **MCP 调用时长**：外部团队里没有长调用 —— 每次工具调用都是短的，长的是 Claude Code 自己的循环。无头试玩这类工具本来就在 Claude Code 的默认超时内。

## 11. 分期

| 期 | 内容 | 验收 |
|---|---|---|
| 0 | 真机验证第 10 节第 1 条 | 两个内联 server 的子 Agent 同时连盒子，盒子看到两条不同的 MCP 会话 |

和上文设计的出入：

1. **没绑定的连接原样透传**（第 4.2 节第 3 条没照做）。盒子分不出一条新连接以后会不会 `team_join`，
   提前拒掉会把普通外部会话（Codex、CLI）一起拒掉。队员的子 Agent 定义里第一步就是 `team_join`。
2. **提示词单独一个文件**（第 5.4 节说的是「用参数区分」）。加参数就要动 `teamPrompt.ts`，
   和「盒子里的团队不受影响」冲突。共用的只有 `DELIVERY_STANDARD` 和 `buildAcceptancePrompt`（原样调用后补一句）。
3. **交付闸拦了几次记在本地**（`.uebox/team.json`），不记在盒子里；没有 `team_round` 这个盒子工具。
   这样 `team_gate` 是只读的，模型自己去调它也不会把次数用掉。
4. **留言是纯信箱**：外部团队没有盒子里 `teamLive` 那套当场插话，`team_message` 只投递，
   多了 `team_inbox` 取信；队员进门时 `team_join` 顺带交给它。
5. **任何角色都不给 `task`**：它跑盒子自己的模型。
6. **队员的命名空间白名单放过 `core`**：`load_skill`、`box_status` 这类基础工具不该因为白名单没写就用不了。
7. **工程没连编辑器时**，执行流上给一个认不出来的连接 id 加工程路径（`offline:<路径>`）：
   编辑器连上时按路径认回来，连不上时报「不存在或已断开」，不会落进旁边另一个连着的工程。
8. 团队工具出现在**每一条**外部会话的清单里（`team_open` 等 11 个），只读档下 `team_snapshot` 按原规则被收掉。
9. 插件没有自带 `.mcp.json`：主会话用用户已经配好的那条 虚幻盒子 连接，免得同一个盒子连两遍、
   制作人在一条上 `team_open`、在另一条上干活。
