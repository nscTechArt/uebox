# 网络资产库在大库上卡死 / 崩溃：根因与修复（2026-10-14）

> 现象来自一个 54 万资产、跑旧版 asset-server-standalone 的团队库：
> 「正在下载资产 (338000/539004)」三条进度挂着不动然后软件崩掉，重启后又从头下；
> 筛选「音频」直接卡死。

## 一句话

桌面端把**整个资产库当成一张小表**来用：所有读写都在主进程（同时负责界面和 IPC）里
同步执行，同步要把几十万行一次性拉进内存再一口气写完，查询则依赖「规划器碰巧选对索引」。
库小时看不出来；到了几十万行，任何一步变成 O(全库) 就是卡死，内存跟着库涨就是崩溃。
过去的修法是哪条慢补哪条，补一个冒一个。

## 根因清单（按「伤害 × 普遍性」排）

| # | 根因 | 表现 | 修法 |
|---|---|---|---|
| 1 | 全量对账「全拉进内存 → 一个事务写完」 | 内存几 GB，进度停在 70% 后崩；进度最后才落盘，重启从 0 开始 | 分页落盘 + 断点续传 + 按时间切片写入（每片 ≤40 ms） |
| 2 | 服务端一行坏数据（父文件夹不在）让整轮对账回滚 | 永远同步不完。实测旧实现跑 54 万行：`FOREIGN KEY constraint failed`，**写进去 0 行** | 坏行只跳过并计数，校验时扣掉 |
| 3 | 对账把「服务端就缺字段」的行塞进缺行缓冲，3 秒后再来一轮对账 | 永远在全量 | 对账不再触发对账；缺行按 key 单取（`GET /assets/:key`） |
| 4 | 旧服务端每次批量导入都要求所有客户端全量（导入不写 change_log） | 有人一导入，所有人重下全库 | 协议缺陷，客户端改不了；让全量足够轻：没变的行不写（实测第二轮 0 行改写） |
| 5 | 每次对账整行重写 → 触发器把每行标成「搜索索引要重建」 | 对账后全库重建全文索引，期间关键词搜索退回全表 LIKE；`updated_at` 被刷成同步时刻 | `UPDATE … WHERE 列 IS NOT 新值`，值没变不写 |
| 6 | 带触发器的写语句，语句日志默认落**磁盘临时文件** | 每插一行建一次临时文件，慢 5 倍 | 保管库连接 `temp_store = MEMORY` |
| 7 | `isDelete` 单列索引（只有 0/1） | 没统计或统计不准时规划器选它：一页从 0.1 ms 变几秒。仓库里已经在三处用 `INDEXED BY` 单点绕过 | 删掉这个索引，回收站改用部分索引 `WHERE isDelete = 1` |
| 8 | 扩展名筛选 `fileExtension IN … OR ext IN …`，`ext` 没索引 | 点「音频」全表扫，54 万行 2.7 s，主线程卡死 | 补 `idx_assetData_ext`；按扩展名筛时不沿排序列索引「边走边筛」 |
| 9 | 列表查询全在主进程同步跑 | 任何慢查询 = 整个软件不响应 | 资产库列表查询挪到 worker 线程（只读连接），worker 不可用时退回主进程 |
| 10 | 实时变更一条一个事务 + 一条 IPC | 同事删一个大文件夹，所有客户端几十万次提交 | 攒批（≤200 条或 30 ms）一个事务，界面收一条汇总通知 |
| 11 | 通知封装把 antd 的 `key` 丢了 | 39 处「先 loading 再用同一个 key 改状态」全部失效；进度条堆成三条永不消失 | `messageManager` 带 key 时原样交给 antd |
| 12 | `start()` 失败时 `emit('error')` 没人监听 → 原地抛出 | 一次超时之后客户端不重连，直到重启 | 有监听才 emit，照常排期重连 |
| 13 | `js-flags` 追加两次，后一次覆盖前一次 | `--max-old-space-size` 从没生效；dev 脚本给 16 GB 堆，正式包没有，dev 测不出 OOM | 合成一个开关，并写明它管不到主进程 |
| 14 | 搜索框没接全文索引 | 每次输入五列 `LIKE '%词%'` 全表扫 | 索引追平走 FTS，没追平退回 LIKE 并推一把后台补齐 |

一个反面教训：给 `ANALYZE` 设 `analysis_limit` 采样提速，会把 `isDelete` 这类低基数列估成
「很有筛选力」（实测从每值 2 万行估成 1001 行），规划器挑错索引，查询慢 900 倍。已撤回。

## 实测（`scripts/bench/network-vault-scale.ts`，54 万资产 / 3000 文件夹）

机器同时在跑别的重任务，墙钟偏长；单步卡顿看 CPU 时间。

| 项目 | 修复前（v1.0.8） | 修复后 |
|---|---|---|
| 首次全量对账 | 下载阶段堆内存 872 MB；写入时第 8 行外键失败，整轮回滚，**写进去 0 行** | 写入 538 999 行，5 行坏数据跳过；峰值堆 67 MB |
| 对账期间单次写入占主线程 | 一个事务写全部（且每轮都失败重来） | 每页 ≤ 0.5 s CPU（按 40 ms 切片提交） |
| 数据没变时再对账一轮 | 54 万行全部重写、全部标记重建搜索索引 | 改写 0 行，标记 0 行 |
| 中途断掉再启动 | 从 0 开始 | 从断点（如第 216 000 行）接着拉 |
| 筛选「音频」（ALL，一页 50 条） | 5 078 ms | 0 ms |
| 不筛选按修改时间倒序 / 大小筛选 | 整表临时排序 | 0 ms |
| 全表读一遍（保管库目录 / 临时目录） | 逐页 ReadFile | 内存映射后快 7~9 倍 / 37 倍 |
| 升级后首次打开建新索引（一次性） | — | 约 2.4 s |

复测：

```bash
node node_modules/jiti/lib/jiti-cli.mjs scripts/bench/network-vault-scale.ts -- --legacy
```

机器忙时墙钟不可信，脚本同时报每一步的 CPU 时间（≈ 空闲机器上会卡多久）。

## 还没修的同类问题（按严重度）

都是「代价随全库增长、在主进程同步执行或把全库搬进内存」：

1. **Ctrl+A / 定位资产把结果翻到底**：`AssetManagement/index.vue` 的 `ensureFilesLoaded` 一页页加载直到没有，
   每页 OFFSET 重查 + 整个列表复制进响应式数组；收藏状态批量查询把所有 key 塞进一个 `IN`，超过约 3.2 万个报错。
2. **递归取整棵子树的整行**：`db:assetData:getByFolderKeyRecursive` 不分页，导入到项目弹窗一打开就调用，
   在 ALL 上就是几十万整行过 IPC。
3. **拖动文件夹**（`dragMoveService.ts`）取整棵子树的整行只为数个数、拿 key。
4. **依赖图「被谁引用」**：`instr()` 扫全部行的 `imports`，约 7 s。
5. **批量上传缩略图**：每张图一次不限条数的名称 LIKE 全表扫。
6. **服务端角色的扫描**（本机当服务器时）：切库就全盘扫描并把全部路径读进两个 Set，新文件逐条自动提交。
7. **浏览单个大文件夹按时间排**：没有 `(folderKey, isDelete, updated_at)` 索引，每页整夹排序。
8. 助手的「资产库概况」九个全表聚合。

根上的方向：

- **查询都过 worker**：这次只挪了资产库列表这一条，上面 2、3、4 都该走同一个 worker，写入留在主进程。
- **列表协议改成游标分页**，不再 OFFSET；「全选」改成「按条件全选」，不把行搬到界面。
- **服务端协议**：批量导入写 change_log，别再逼全员全量。旧服务端只修严重问题，这条留给新后端。
- **按客户规模做回归**：`scripts/bench/network-vault-scale.ts` 动过同步或查询路径就跑一次。
